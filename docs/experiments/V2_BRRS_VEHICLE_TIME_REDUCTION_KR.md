# V2 차량 실험 시간 단축: 안전 경계와 적용 순서

작성: 2026-09-28. **설계·오프라인 감사 문서**이며 현재 실행기, 매니페스트, 펌웨어, STOP, 원본 로그, 공식 판정을 변경하지 않는다. 집은 기능·회귀 테스트 장소이고 논문 본 데이터는 차량에서 수집한다. 이 문서의 절감안은 차량 RF 실행 승인이 아니다. [V2 실험 표준](V2_BRRS_EXPERIMENT_STANDARD_KR.md)의 기본 825케이스, 조건부 최대 906케이스를 대상으로 한다. V2 목록은 아직 현재 실행기의 실제 생성 목록이 아니다.

## 1. 확인된 시간과 확인되지 않은 시간

- V2 기본 825케이스는 Stage0/confirmation 132회(각 2,000 superframe), 나머지 693회(각 1,000 superframe)다. 10 ms/superframe의 명목 RF 구간 합계는 `132×20 + 693×10 = 9,570초 = 2시간 39분 30초`다. 보드 시작·종료와 재시도는 포함하지 않는다.
- 이전 Ubuntu→Air 차량 Stage0의 완료 94건에서 `results/orchestration.json` 기준 케이스 내부 중앙값 48.35초, 다음 케이스까지 간격 중앙값 61.86초였다. 내부 시작→모든 TX READY는 중앙값 11.17초, READY→종료는 37.17초다. 첫 시작~마지막 종료는 2.878시간이다. **이는 Stage0/구전송 경로의 관측이지 V2 Exp4 시간 예측이 아니다.**
- 별도 Air-native 실행의 모니터 스냅샷은 2026-09-14 11:10:49 KST 완료 13건에서 14:38:00 KST 완료 193건으로 증가했다. 이 구간 평균은 약 69.1초/케이스다. Stage0와 일부 Exp2가 섞인 구간이며 V2 전체 예측으로 외삽하지 않는다.
- Exp4가 576/825건(69.8%)을 차지한다. 따라서 모든 케이스의 고정비가 10초 줄면 차량 시간이 2시간 17분 30초 단축된다. Exp4에서만 10초 줄어도 1시간 36분이다. 이는 산술적 민감도이며 실현된 절감량이 아니다.

현재 실행기는 매 attempt마다 전체 계획에서 단일 케이스를 준비하고, 정적 도구·소스 증거·HEX/ELF를 케이스 번들에 복사/해시하며, Air-native일 때도 번들을 별도 경로에 복사하고 결과를 다시 복사한다. 보드는 케이스별 READY 후 RF, 결과/metadata/HEX readback/HALT 및 공식 assessment를 검증한다. 이 작업들의 **개별 소요시간은 아직 계측되지 않았으므로** 느린 원인을 한 단계로 단정하지 않는다.

## 2. 케이스 경계에서 절대 잃지 않을 증거

Exp 전체를 RF부터 끝까지 먼저 실행하고 검증을 마지막에 몰아 하는 방식은 채택하지 않는다. 설정·케이블·이미지·수집 오류가 생긴 시점과 영향을 받은 케이스를 특정하기 어렵고, 오류 뒤 차량 시간을 계속 소비할 수 있다. 다음은 **각 케이스 다음 RF 전에** 확인한다.

1. 고유 case/attempt ID, 실제 환경·PHY·lead·물리 역할·slot sequence와 기대 펌웨어 해시가 일치하고, STOP/소유권·활성/비활성 보드 상태가 안전하다.
2. 모든 TX READY 후 RX가 시작했고 목표 superframe 및 END가 확인되며, 원시 로그와 metadata의 case/serial/역할/해시/행 수가 완전하다.
3. 그 케이스의 공식 PASS/FAIL_PER/INVALID와 운영상 중단 조건을 즉시 평가한다. 유효한 PER 실패를 후속 반복의 성공으로 덮지 않는다.
4. 활성 보드의 설치 HEX 전체 readback, 전 보드 HALT·수집 프로세스 종료가 검증된다. 오류 또는 사용자 환경 변화 시 다음 RF를 막는다.

따라서 `READY`를 반복할 필요가 없다는 가정이나 full HEX readback을 Exp 끝에 한 번만 하는 안은 현재 **불채택**이다. RF마다 보드가 새 실행을 시작하고, 이미지가 변경되거나 메모리가 달라질 수 있다. 마지막 readback만으로 앞선 케이스의 이미지 일치를 소급 입증할 수 없다.

## 3. 적용 순서 — 케이스 수·12블록 회전은 유지

| 순서 | 차 밖/차 안의 변경 | 안전 조건 및 채택 기준 |
| --- | --- | --- |
| 0. 계측 | 격리 실행기 복사본에 monotonic 경계 시각만 추가: 계획 생성, cache 확인/빌드, 번들 봉인, 복사, preflight, 플래시/READY, RF, 결과 복사, readback/HALT, assessment/postflight. 프레임 처리 경로에는 계측을 넣지 않는다. | 집에서 대표 Stage0·Exp2·Exp3·Exp4(S1/S6)·Exp5 소규모 테스트로 기존 결과/해시·순서 동일성 확인. 7보드 Exp4가 병목인지는 계측 후 판단. |
| 1. 차량 밖 준비 | 고정 CH5/PHY/도구/소스와 Stage0 lead grid용 이미지를 Air의 **격리 캐시**에 미리 빌드·검증한다. 실제 차량 환경·보드 위치·Stage0 선정 lead는 현장에서 새 manifest에 기록한다. | 빌드 도구/소스/옵션/HEX/ELF 해시로 정확히 일치할 때만 재사용. Stage0 전 과거 차량 lead를 동결값으로 넣지 않는다. 캐시 불일치는 RF 전 중단 또는 검증된 새 빌드로 처리한다. Ubuntu 불량 RAM에서 빌드하지 않는다. |
| 2. 중복 준비·복사 축소 | 매 케이스 동일한 SDK 도구/이미지를 다시 복제하지 않도록 읽기 전용 content-addressed 저장소를 두고, 케이스별 manifest·조건·해시·원시 결과만 고유 경로에 봉인한다. Air-native의 불필요한 로컬 왕복 복사를 제거한다. | 케이스가 독립 검증 가능해야 하며 cache 파일 변경/누락 시 RF를 막는다. 원본 case root는 불변, 재시도는 새 attempt. 동일 조건의 12블록을 합치거나 원본을 덮지 않는다. |
| 3. 결과 처리 분리 | 매 케이스의 위 2절 최소 게이트와 공식 판정은 즉시 수행한다. 논문용 CIR 상세 집계·표/그림 생성·원격 백업은 Air 원본을 해시·완전성 확인한 뒤 블록 경계 또는 차량 반납 후 수행한다. Exp4는 48케이스/블록마다 누락·디스크 여유·전송 상태를 체크한다. | raw/meta/assessment가 Air의 불변 케이스 경로에 이미 안전하게 남아야 한다. 디스크·수집·판정 오류는 블록 끝까지 미루지 않는다. 백업 지연이 허용되는지는 저장공간·전원·복구 시험으로 별도 확인한다. |
| 4. 동일 이미지 재사용 후보 | 정확히 같은 HEX가 이미 설치된 반복에서 플래시를 생략하고 검증된 reset-only 경로를 쓸 가능성을 집에서 별도 A/B 시험한다. | 현재 Standard에는 자동 적용하지 않는다. 기존 reset-only 진단과 재flash 관측은 실험 조건 차이 가능성이 있어 동등성이 입증되지 않았다. 매 케이스 사전/사후 이미지 검사와 HALT는 유지하고, 시스템·PER·타이밍의 동등성 기준을 통과해야 한다. |
| 5. 실험 수 축소 | 위의 무손실 절감으로도 렌트 예산을 맞출 수 없을 때만 논문 목표와 반복력에 대한 별도 결정을 받는다. | Stage0의 0–40/PAC 톱니 경계, Exp4의 12블록·6역할 2회 회전, Exp3 짝 반복, 링크별 Exp2/5 반복을 임의 축소하지 않는다. |

### 단계·블록 경계에서 묶어도 되는 것

- **시작 전 한 번:** 설치 사진·물리 위치·serial·전원/USB/네트워크·환경 기록, 정적 source/toolchain 해시와 Air 여유 공간. 연결이 바뀌면 해당 항목을 재확인한다.
- **Stage0 이후:** 새 차량 lead 선택/confirmation을 검증하고, 그 lead에 의존하는 후속 이미지·case manifest를 봉인한다. 이 단계 전에는 후속 케이스를 임시 lead로 실행하지 않는다.
- **Exp4 매 48케이스 블록:** 역할 회전과 원본 수량/누락, 디스크·전원·환경 drift를 요약한다. 오류·STOP은 블록 종료를 기다리지 않고 해당 케이스에서 즉시 처리한다.
- **차량 반납 후:** 원본을 보존한 채 재계산 가능한 집계·통계·표·그림 및 논문용 대량 백업/정리. 이는 케이스의 공식 판정을 뒤로 미룬다는 뜻이 아니다.

## 4. 출시 게이트와 절감시간 판단

각 최적화는 **격리된 새 실행기**에서만 개발하고, 집의 대표 케이스로 구 실행기와 A/B 비교한다. case 순서·PHY·역할·RF 설정·원시 로그·공식 판정·STOP·readback/HALT가 동일해야 한다. 중단/수집 실패/캐시 오염/전원·USB 변경을 주입한 오프라인·소규모 시험에서 다음 RF가 차단되는지도 확인한다. Stage0 및 Exp4 각각의 실제 절감 중앙값·p90과 추가 오류율을 기록하고, 절감이 미미하거나 증거가 약하면 구 방식으로 되돌린다. **차량 실험에서 처음 검증하지 않는다.**

현재 상태: 과거 로그 감사와 안전 경계만 작성했다. V2 실행기 전환, 캐시, 지연 백업, reset-only, RF는 아직 구현·실행하지 않았다. 실제 단축 시간은 순서 0의 계측 및 집 A/B 테스트 전에는 약속할 수 없다.
