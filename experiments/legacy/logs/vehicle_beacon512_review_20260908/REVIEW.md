# 비컨 256/512 성능 및 펌웨어 검토

검토 범위는 기존 소스·빌드 ELF·실행 로그·플래시 검증 기록이다. 이번 검토에서는 보드에 접근하거나 RF를 추가 실행하지 않았고 펌웨어/Git 상태를 변경하지 않았다.

**결론: 512 적용 누락이나 송수신 타이밍 불일치는 발견하지 못했다. 그러나 현재 자료로 256과 512의 성능이 같다고 결론낼 수 없다. 기존의 비컨 단절 100ms 조기 종료가 약한 링크의 관측을 끊는 동작도 확인했다.**

## 512 변경 검증

API 소스 복사본을 대조했을 때 359개 파일은 같고, 변경 파일은 INIT C, NORMAL C, 감독 수집기 Python의 3개뿐이었다. 펌웨어 변경은 양쪽 C의 `SYNC_PLEN` 및 `SYNC_PREAMBLE_SYMBOLS` 256→512다. 수집기 변경은 한 노드 실패 시 나머지 제한 시간 내 수집을 기다리는 것으로, 실패 검증은 그대로 유지한다.

| 항목 | 256 | 512 |
|---|---:|---:|
| 비컨 프리앰블 실제 설정 | 256 | 512 |
| 비컨 PAC | 8 | 8 |
| 비컨 SFD timeout | 257 | 513 |
| 비컨 airtime 모델 | 337µs | 598µs |
| 비컨 RMARKER offset | 269µs | 530µs |
| 다음 비컨 RX 개시 offset | 9,719µs | 9,458µs |
| 비컨 RX 창 | 349µs | 610µs |
| RX 창 끝, 이전 비컨 RMARKER 기준 | 10,068µs | 10,068µs |
| DATA | M32/PAC8, lead26 | 동일 |
| DATA 슬롯 수 / 간격 | 13 / 347µs | 동일 |

7개 ELF의 `config_sync`를 다시 추출해 길이 코드 0x1F→0x3F 및 SFD timeout 257→513을 확인했다. `config_data`는 7개 모두 이전 ELF와 바이트 단위로 같다. 세부 값은 `REVIEW.json`에 보존했다. 모든 실험의 기록에는 대상 HEX와 실제 MCU 플래시의 readback PASS가 있다.

실행 로그도 INIT `sync_plen=512`, TX `sync_frame_us=598`, `sync_rx_window_us=610`과 일치한다. 512의 N4–N7은 각 실행마다 비컨 1,000/1,000 및 DATA TX 2,000/2,000을 완료했다. 첫 512 실행에서 비컨 delayed-TX late=0, 다음 비컨 준비 완료 잔여 여유 최소 842µs였다. 따라서 512를 설정했는데 실제로는 256이거나, 수신창을 늘리지 않아 모두 잘리는 형태의 오류를 지지하지 않는다.

이는 소스·ELF·로그·플래시 검증이다. 별도 장비로 송신 RF 파형의 프리앰블 지속시간을 직접 측정한 것은 아니며, 약한 링크에서만 드러나는 드라이버/하드웨어 동작을 모두 배제하는 증거도 아니다.

## 기존 펌웨어의 100ms 조기 종료

NORMAL Exp4는 마지막으로 받은 비컨을 기준으로 다음 동작을 한다.

1. 약 27ms 비컨 단절 시 SYNC PHY로 복귀하고 즉시 RX를 열어 재획득을 시도한다.
2. 약 100ms까지 다음 비컨을 받지 못하면 END 통계를 출력한다.
3. `dwt_forcetrxoff()` 후 메인 루프에서 `break`하여 해당 실행을 종료한다.

이 동작은 256과 512 소스 모두에 존재한다. 관련 코드:

- [timeout에 따른 최종 통계 진입](/Users/songchieon/Desktop/DWM3000/DW3_QM33_SDK_1.0.2_vehicle_beacon512_20260908/Drivers/API/Src/examples/ex_35b_brrs_normal/brrs_normal.c:1424)

N3가 비컨 3개 또는 28개를 받은 뒤 빠르게 종료된 현상과 부합한다. 그 뒤 남은 슬롯은 재획득을 시도하지 않은 채 미송신으로 남는다. 이는 원래 발생한 비컨 수신 실패의 원인과 별개로, 장시간 약한 링크 평가를 중단시키는 기존 실험 종료 정책이다. 512 변경에서 새로 생긴 문제는 아니다.

반면 처음부터 비컨 0개인 N2 등은 `last_sync_cycles != 0` 조건에 들어가지 않는다. 초기에는 50ms RX timeout 뒤 다시 즉시 RX를 열며, 끝까지 첫 비컨을 받지 못하면 호스트의 60초 수집 timeout으로 끝났다. 따라서 비컨 0개 현상을 100ms 조기 종료로 설명해서는 안 된다.

## 관측으로 구분되는 두 문제

- 범퍼: 비컨 획득/유지가 실패한다. 첫 대시보드 512에서 N3가 28개 비컨을 받고 84번 DATA를 송신했지만 DATA 수신은 0개였다. 따라서 비컨만 수신 가능해져도 uplink DATA가 자동으로 해결된다는 근거는 없다.
- N4–N7: 비컨은 이미 1,000개 모두 수신하고 모든 DATA를 송신했다. 이들의 남은 PER은 현재 로그에서 DATA 수신 단계 손실이다. 비컨 프리앰블만 늘리고 DATA M32·PAC8·lead26·송신 출력 등을 유지한 이번 변경은 이 DATA 링크를 직접 강화하지 않는다. 간접적인 수신 상태/채널 변화 효과까지 없다고 단정하는 것은 아니다.

현재 범퍼 TX 로그는 비컨 RX 오류 합계만 제공하며 프리앰블 검출, SFD, PHR, CRC 실패를 각각 분해하지 않는다. INIT의 SFD/RXFSL 카운터는 DATA 수신 구간에서 나온 것으로 범퍼의 비컨 실패 원인으로 가져다 쓰면 안 된다. 비컨 전체가 디코드되지 않았다는 것과 프리앰블이 전혀 검출되지 않았다는 것은 같지 않다.

## 제조사 자료와 PAC 해석

[Qorvo DW3xxx API Guide](https://forum.qorvo.com/uploads/short-url/xD3TlXKvkujjdUaJWXv2b4E7GQN.pdf)의 `dwt_configure()` 설명, 인쇄 페이지 36 Table 3/4는 높은 데이터율에서 프리앰블을 과하게 늘려도 추가 거리 이득이 제한될 수 있다고 설명한다. Table 4의 조건별 권장은 6.81Mb/s에서 M32/PAC4, M≥64/PAC8이다. 현재 비컨 PSDU 속도는 6.8Mb/s다.

같은 문서의 enum 주석 및 사용 중 SDK 헤더에는 데이터율 구분 없이 256/PAC16, 512/PAC32라는 설명도 있어 문서 내부의 표현이 일관되지 않는다. 따라서 enum 주석만 근거로 이번 512/PAC8을 설정 오류라고 판정하지 않는다. 속도별 권장표에 비춰 PAC8 유지가 곧 실수라는 증거는 없다. 이것이 차량 채널에서 PAC8의 최적성을 입증하는 것은 아니다.

프리앰블을 늘리면 검출/추정에 쓸 신호 시간이 늘지만 SFD·PHR·비컨 PSDU 자체를 더 길고 강한 부호로 바꾸는 것은 아니다. 링크가 충분히 약하거나 후속 필드 디코딩이 병목이면 패킷 성공률 개선이 드러나지 않을 수 있다. 현재 채널의 정확한 감쇠/간섭 원인은 측정되지 않았으므로 금속 차폐, 방향, continuous RX 중 하나로 확정하지 않는다.

## 비교의 한계와 다음 진단

직전 대시보드 M256은 RX 최종 통계 전에 감독 수집기가 전체 실행을 중단했다. M512는 다른 보드의 수집을 끝까지 기다리도록 한 뒤 RX 1,000SF를 확보했다. 따라서 두 결과를 동등한 완주 PER A/B로 비교할 수 없다. N3의 비컨 3→28도 서로 다른 단절/종료 구간의 관측이므로 개선 배율이 아니다. 이후 N2 방향 및 RX 위치를 바꾼 실행들은 비컨 길이 A/B가 아니다.

다음 진단에서는 100ms 단절을 최종 종료와 분리하고, 고정한 전체 관측 시간 동안 비컨 재획득을 계속 시도하되 미수신/미송신 슬롯을 그대로 손실로 기록하는 것이 우선이다. 재전송으로 손실을 숨길 필요는 없다. 함께 비컨 RX 오류를 검출/SFD/PHR/CRC로 나누고, 같은 배치에서 256과 512를 비교해야 프리앰블 효과를 판정할 수 있다. 필요하면 별도 진단 모드에서 DATA/PHY 전환을 제거한 비컨 전용 측정으로 공통 펌웨어 영향과 실제 링크를 분리할 수 있다. 이번 검토에서는 이 구현이나 추가 RF를 실행하지 않았다.
