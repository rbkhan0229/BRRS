# 자택 비컨 RX 오류·복구 시각 계측과 600µs 수신창 비교

결론: **600µs 후보를 채택하지 않는다.** AUX ON에서 비컨 누락은 800µs 기준 9/2000에서 후보 2/2000으로 적었지만, DATA 수신은 1978/2000에서 1965/2000으로 줄고 offered PER은 공식 **FAIL_PER 1.10% → FAIL_PER 1.75%**였다. 각 ON 1회씩 다른 시각의 관측이므로 비컨 감소의 인과 효과도 확정할 수 없다. 자택 단일 링크 진단이며 차량 Stage0·Exp4·Standard 결과에 넣지 않는다.

Air 원본 root:
- 기준: `/Users/songchieon/Desktop/DWM3000/logs/home_beacon_rearm_timing_20260930_215100`
- 후보: `/Users/songchieon/Desktop/DWM3000/logs/home_beacon_rearm_window600_20260930_222000`

Ubuntu 동기화 root는 각각 `/home/chieon/DWM3000/logs/` 아래 같은 이름이다. 보존 원본의 재분석 결과는 이 root의 `CLOCK_ANCHOR_EFFECT_ANALYSIS.json`이며 재현 코드는 `analyze_clock_and_effect.py`이다.

조건: 사용자가 재확인한 자택 INIT–N7 약 30cm, AUX–INIT 약 1m, USB·전원 그대로, 통행·작업 없음. CH5, 비컨 M512/code10, DATA M64/PAC8/code11, 임시 lead44µs, 10ms×2000SF, 단발 비컨 누락 예측송신 ON, AUX CH5 M64/code9/1009µs/index40. INIT=1050270933, N7=1050204212, 수동 N2=1050211584, AUX=1050257038. 위치·간섭 수준이 네 관측 사이에 완전히 일정했다는 계측은 없다.

OFF→ON은 각 root에서 직렬로 한 번씩만 실행했고 자동 재시도는 없었다. 기준 ON의 누락 비컨 9건과 후보 ON의 2건은 모두 1회 예측 송신으로 처리되어 미송신 0이다. 후보의 전체 PER 악화는 이 관측에서 송신 후 손실 22→35와 일치한다. AUX는 각 ON 수집창에서 TXFRS 증가 24,872/24,489개로 지속 송신 검증 PASS였으나 두 창의 간섭 위상까지 동일하지 않다.

계측 수정은 격리된 N7 코드의 정상 CRC 비컨 처리 후마다 DW3000 SYS_TIME 래치를 W1C=0으로 해제하고, 무선 시각 읽기 직전·직후 MCU cycle을 저장하는 것이다. 누락 전후 정상 비컨의 두 앵커로 기존 RX 오류 상태 폴링과 재활성화 API 반환의 MCU 시각을 DW3000 시각으로 보간했다. 오류 복구 경로에는 새 SPI 읽기를 넣지 않았다. 앵커 읽기 폭은 관측 최대 약 42.4µs다. 이는 실제 무선기가 RX 상태로 복귀한 순간을 직접 측정하지 않으며, 시계 보간·폴링 지연이 남는다.

기준 ON의 누락 9건에서 오류 **상태 폴링**은 예상 비컨 RMARKER −83~+124µs, RX-enable **API 반환**은 +241~+449µs로 추정됐다. 후보 ON의 누락 2건은 각각 오류 상태 +79/+118µs, 반환 +404/+442µs였다. 둘 다 비컨 이후에 복구 반환이 기록된 사례다. 오류 신호가 AUX인지 INIT인지, 내부 수신기가 비컨 프리앰블을 어느 지점까지 검출했는지는 여전히 미분리다. 새 앵커 기울기는 3.833~3.839 DW high32 tick/MCU cycle이어서 기존 고정 64MHz CPU 환산값을 절대 무선 시각으로 그대로 쓰지 않았다.

후보는 N7의 예정 SYNC delayed-RX 시작만 800µs 전(199680 high32 tick)에서 600µs 전(149760 tick)으로 바꿨다. M512+8-symbol SFD 명목 RMARKER 오프셋은 약 529µs이므로 이 설정은 약 71µs 먼저 RX를 열도록 의도했다. 후보 root의 `SOURCE_DELTA.txt` 기준 C 변경은 이 한 줄뿐이며, trace 헤더·host verifier·실행기는 같고 INIT/N2/AUX HEX도 동일하다. N7 HEX SHA256은 기준 `0565d3bad300a78f8804ffec44660e1e1da1602ba53d909bf196b5716a81caee`, 후보 `07be62a1583dfeb53e0331e68275e321b5ffd824e5c62ba171fa4d68d607ba89`다. 각 case의 `bundle/provenance/build_toolchain.json`, `source_git.json`, `board_manifest.json`, `payload_hashes.json`에 도구·소스·manifest·payload provenance가 봉인돼 있고, Ubuntu 동기화본 4×134개 payload 파일 해시 검증 PASS다. Air SES 8.28 빌드 PASS, 격리 controller 165 tests PASS(4 기존 fixture SKIP).

각 case의 수집/metadata/READY/END/flash readback과 비컨 trace 무결성 PASS; 시스템 오류·trace overflow 0. 마지막 Air `FINAL_HARDWARE_AUDIT.json`: 8대 모두 HALT·3300mV, 활성 INIT/N2/N7/AUX 전체 HEX readback PASS, 수집기 0, 각 case/root/global STOP 존재. 기존 root·case STOP과 공식 판정은 변경하지 않았다. 추가 RF 예약 없음.

이 결과는 후보 ON에서 비컨 누락 수가 적었다는 단일 관측일 뿐이며 재현성은 미확인이다. 시스템 목표 PER<1%도 충족하지 못했다. 다음 조치는 이 후보를 채택해 차량 Standard로 넘기는 것이 아니라, 수신기 내부 오류/재활성화가 실제 RF 수신에 미치는 영향과 AUX 위상을 통제해 원인을 다시 분리하는 것이다. 사용자 새 지시 전 추가 RF는 없다.
